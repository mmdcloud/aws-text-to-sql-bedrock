# MySQL 8.0 Dialect & Query Safety Guidelines

This document establishes the mandatory SQL syntax rules, dialect standards, and security constraints for all SQL statements generated by Amazon Bedrock for execution against the application's Amazon RDS MySQL database.

---

## 1. Security & Read-Only Constraints (Crucial)

1. **Strictly `SELECT` Statements Only**:
   - The database user and application runtime enforce read-only execution.
   - **Never** generate `INSERT`, `UPDATE`, `DELETE`, `DROP`, `TRUNCATE`, `ALTER`, `CREATE`, `REPLACE`, `MERGE`, `GRANT`, or `REVOKE`.
   - **Never** attempt to call stored procedures (`CALL`) or execute metadata modification commands.
2. **No Access to System Schemas**:
   - Do **not** query `information_schema`, `performance_schema`, `mysql`, or `sys` tables.
   - Do **not** execute administrative statements (`SHOW PROCESSLIST`, `SHOW VARIABLES`, `SHOW STATUS`).
3. **No Multi-Statement Injections**:
   - Queries must always be a single, standalone `SELECT` statement.
   - Do not terminate with semicolons followed by additional commands.

---

## 2. Dialect Standards for MySQL 8.0

### A. Date and Time Functions
* Current timestamp: Use `NOW()` or `CURRENT_TIMESTAMP`.
* Date subtraction: Use `DATE_SUB(NOW(), INTERVAL 30 DAY)` or `NOW() - INTERVAL 7 DAY`.
* Date formatting: Use `DATE_FORMAT(column, '%Y-%m-%d')` or `DATE_FORMAT(column, '%Y-%m')` for monthly aggregations.
* Date difference: Use `DATEDIFF(end_date, start_date)` for difference in days.
* Time elapsed in custom units: Use `TIMESTAMPDIFF(MINUTE, start_time, end_time)` or `TIMESTAMPDIFF(DAY, ...)`.
* Avoid non-standard functions from PostgreSQL (`TO_CHAR`, `AGE`) or SQL Server (`GETDATE`, `DATEPART`).

### B. String Operations
* String concatenation: Use `CONCAT(first_name, ' ', last_name)` or `CONCAT_WS(' ', ...)`. Do **not** use the `||` operator.
* Pattern matching: Use `LIKE '%keyword%'` (case-insensitive in standard utf8mb4 collation).
* Regular expressions: Use `REGEXP_LIKE(column, 'pattern')` or `column REGEXP 'pattern'`.
* Substrings: Use `SUBSTRING(column, start, length)` or `LEFT(column, length)`.

### C. Null Safety & Coalescing
* When summing nullable fields or running outer joins, always wrap in `COALESCE(SUM(amount), 0.00)` to ensure a clean numerical output rather than `NULL`.
* For inline conditions: Use `IFNULL(val, default)` or `CASE WHEN ... THEN ... ELSE ... END`.

### D. Group By & Aggregation Rules
* In MySQL 8.0 (`ONLY_FULL_GROUP_BY` is enabled by default):
  - Every non-aggregated column in the `SELECT` list **must** appear in the `GROUP BY` clause.
  - Do **not** select columns not included in `GROUP BY` unless wrapped in an aggregate function (`MIN`, `MAX`, `AVG`, `SUM`, `COUNT`, `ANY_VALUE`).

### E. Window Functions and CTEs
* MySQL 8.0 natively supports Common Table Expressions (`WITH ... AS (...)`) and Window Functions (`ROW_NUMBER() OVER (...)`, `RANK() OVER (...)`, `DENSE_RANK() OVER (...)`, `SUM() OVER (...)`).
* Prefer CTEs over deeply nested subqueries for readability and optimizer plan clarity.

---

## 3. Performance & Resource Constraints

1. **Mandatory Limit on Open-Ended Queries**:
   - Queries listing individual rows (not aggregate summaries) must always include an explicit `LIMIT` clause (e.g., `LIMIT 50` or `LIMIT 100`).
   - The application enforces a hard ceiling of 1000 rows.
2. **Avoid `SELECT *`**:
   - Always name explicitly required columns (e.g., `SELECT o.order_id, o.order_date, c.email`).
   - `SELECT *` wastes network bandwidth, invalidates index coverage, and can break front-end data tables.
3. **Use Existing Indexes**:
   - When filtering by status or date:
     - `orders`: indexed on `(status)`, `(order_date)`, `(customer_id)`.
     - `customers`: indexed on `(status)`, `(customer_tier)`, `(created_at)`.
     - `products`: indexed on `(category_id)`, `(retail_price)`.
     - `subscriptions`: indexed on `(status)`, `(customer_id)`.
